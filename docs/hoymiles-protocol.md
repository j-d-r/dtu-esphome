# Hoymiles RF protocol reference

This page describes, byte by byte, what a DTU and a Hoymiles microinverter
send to each other over the air: how they find each other, which packets they
exchange, what each field means and how the checksums are computed. It covers
HM and HERF inverters (2.4 GHz, nRF24L01+) and HMS inverters (sub-GHz,
CMT2300A). Both radios carry the same application protocol.

For *how this component implements it* (state machines, timeouts, retries),
see [rf-protocol.md](rf-protocol.md). The code that builds and parses every
packet below is `components/hoymiles_dtu_base/protocol.{h,cpp}`.

The protocol is undocumented by Hoymiles. Everything here comes from
[Ahoy](https://github.com/lumapu/ahoy), [OpenDTU](https://github.com/tbnobody/OpenDTU),
the CCC report *"Wireless Interface Vulnerabilities of Hoymiles
Microinverters"*, and captures made while developing this component. The
[status](#verification-status) section says which parts were checked on
real hardware.

## Conventions

- All bytes are hexadecimal. `[n]` is the byte at index `n` of a packet,
  `[a..b]` the bytes `a` to `b` inclusive.
- Multi-byte numbers are **big-endian** (most significant byte first), unless
  stated otherwise.
- The examples use made-up identities so that no real device appears in
  this document:

  | Role | Printed serial | Model |
  | --- | --- | --- |
  | HM inverter | `116100000000` | HM-1200 (4 inputs) |
  | HMS inverter | `114400000000` | HMS-800 (2 inputs) |
  | DTU | `80000000` | this component |

  Because the serials end in zeros, the address bytes in the examples are
  `00 00 00 00`. With a real serial they carry its last eight digits, as
  explained in [Identities](#identities-serials-and-addresses).
- Every hex dump was generated by this repo's packet builders and checked by
  its parsers, so the CRCs in them are correct. Measurement values in replies
  are invented.

## Radio layer

| | HM / HERF | HMS |
| --- | --- | --- |
| Chip | nRF24L01+ | CMT2300A |
| Band | 2.4 GHz | 860 MHz (EU) or 900 MHz (US, Brazil) |
| Modulation | GFSK, 250 kbit/s | GFSK, 20 kbit/s, 20 kHz deviation |
| Frequencies | hops over channels 3, 23, 40, 61, 75 (2403 … 2475 MHz) | one fixed frequency, 250 kHz channel steps |
| Addressing | 5-byte hardware address | none, filtered in software |
| Link CRC | CRC16, added by the chip | CRC16, added by the chip |
| Auto-ACK | yes, hardware | no |
| Max payload | 32 bytes, dynamic length | 32 bytes, length-prefixed FIFO |

The radio adds its own preamble, address or sync word and link CRC. Those
bytes never reach the application. Everything below is the *payload* the
chip delivers: the bytes written to the TX FIFO, or read back from the RX
FIFO.

HMS frequencies are `base + channel × 250 kHz`:

| Region | Base | Allowed | DTU work frequency | Inverter boot frequency |
| --- | --- | --- | --- | --- |
| EU | 860 MHz | 863–870 MHz | 865 MHz (channel 20) | 868 MHz (channel 32) |
| US | 900 MHz | 905–925 MHz | 918 MHz (channel 72) | 915 MHz (channel 60) |
| Brazil | 900 MHz | 915–928 MHz | 918 MHz (channel 72) | 915 MHz (channel 60) |

## Identities: serials and addresses

### The printed serial is hexadecimal

An inverter's 12-digit serial (on its label, e.g. `116100000000`) is
**hexadecimal**: it is six bytes, `11 61 00 00 00 00`. Some models even
print letters (HMS prefix `114A`). Reading it as a decimal number gives a
completely different value, and the inverter will never answer.

- The first four digits (`1161`) give the model family. They are never sent
  over the air.
- The last eight digits (`00000000`) are the inverter's identity on the
  radio. Call them `S3 S2 S1 S0`.

### Inverter ID in packets

Inside packets, the inverter is identified by the last four bytes of its
serial in printed order:

```
printed serial   11 61 | S3 S2 S1 S0
packet [1..4]            S3 S2 S1 S0
```

For example, a serial ending in `12345678` appears as `12 34 56 78`. Our
dummy HM inverter appears as `00 00 00 00`.

### nRF24 radio address

The nRF24 address is `01` followed by the same four bytes. Written as the
5-byte array handed to the chip's address register (byte 0 first):

```
inverter address   01 S3 S2 S1 S0      dummy HM:  01 00 00 00 00
DTU address        01 D3 D2 D1 D0      dummy DTU: 01 80 00 00 00
```

The DTU transmits to the inverter's address (and also listens on it on
pipe 0, to receive the hardware ACK). It receives replies on its own address,
on pipe 1. HMS has no hardware address. A HMS receiver gets every packet on
its frequency and keeps only those that carry its own DTU serial in `[5..8]`.

### DTU serial

The DTU also needs a 4-byte serial, `D3 D2 D1 D0`. The inverter sends its
replies to that ID. Any value works if it is unique among DTUs in range and
stays the same: an HMS inverter remembers the DTU it is bound to. Hoymiles
DTUs and Ahoy use `0x8` followed by seven digits. This component builds
them from the ESP32's MAC (`hm_generate_dtu_serial`). The examples use
`80 00 00 00`.

## Packet structure

Every request and every reply uses the same layout:

```
 [0]      [1..4]         [5..8]         [9]      [10 .. n-2]   [n-1]
┌────────┬──────────────┬──────────────┬────────┬─────────────┬──────┐
│ opcode │ inverter ID  │ DTU serial   │ index  │ data        │ CRC8 │
└────────┴──────────────┴──────────────┴────────┴─────────────┴──────┘
```

| Field | Meaning |
| --- | --- |
| opcode | The command. A reply uses the request's opcode with bit 7 set (`0x15` → `0x95`, `0x51` → `0xD1`). |
| inverter ID | Last four serial bytes of the target inverter (requests) or of the sender (replies). |
| DTU serial | The DTU's ID. In a request it says where to reply. A reply repeats it. |
| index | Fragment/packet index. See the table below. |
| data | Depends on the opcode. In requests that carry one, the data ends with a CRC16. |
| CRC8 | Over every previous byte, `[0..n-2]`. Always present. |

Values of the index byte `[9]`:

| Value | Used in |
| --- | --- |
| `80` | a multi-frame request (realtime data and the other data types) |
| `81` | a single-frame DevControl request, and its reply |
| `8k` | re-request of fragment `k` (`k` = 1…7) |
| `01`…`07` | reply fragment `k` that is not the last one |
| `80` + `k` | reply fragment `k` that is the last one, e.g. `84` = fragment 4 of 4 |

Bit 7 of the index is the "last fragment" flag, and bits 6..0 are the
fragment number, starting at 1.

## Checksums

The application protocol has two checksums. They come on top of the CRC the
radio chip already adds.

### CRC8: one per packet

| Parameter | Value |
| --- | --- |
| Polynomial | `0x01` (x⁸ + 1) |
| Initial value | `0x00` |
| Reflected | no |
| Final XOR | none |
| Covers | every byte of the packet before it |

```c
uint8_t crc8(const uint8_t *data, size_t len) {
  uint8_t crc = 0x00;
  for (size_t i = 0; i < len; i++) {
    crc ^= data[i];
    for (int bit = 0; bit < 8; bit++)
      crc = (crc & 0x80) ? (uint8_t)((crc << 1) ^ 0x01) : (uint8_t)(crc << 1);
  }
  return crc;
}
```

Test vectors: `15 01 02 03 04` → `11`; ASCII `123456789` → `31`.

### CRC16: one per command or record

| Parameter | Value |
| --- | --- |
| Algorithm | CRC-16/MODBUS |
| Polynomial | `0x8005`, reflected (`0xA001` in the shift-right form below) |
| Initial value | `0xFFFF` |
| Final XOR | none |
| Byte order on air | **big-endian** (high byte first, unlike real Modbus) |

```c
uint16_t crc16(const uint8_t *data, size_t len) {
  uint16_t crc = 0xFFFF;
  for (size_t i = 0; i < len; i++) {
    crc ^= data[i];
    for (int bit = 0; bit < 8; bit++)
      crc = (crc & 0x0001) ? (uint16_t)((crc >> 1) ^ 0xA001) : (uint16_t)(crc >> 1);
  }
  return crc;
}
```

Test vectors: `0B 00 01 02 03 04 05` → `7BAF`; ASCII `123456789` → `4B37`.

Where it is used:

- **Requests with command data** (`0x15` data requests and `0x51`
  DevControl): the CRC16 covers `[10]` up to the byte before it. The CRC8
  then covers the whole packet, CRC16 included.
- **Reply records**: the inverter appends a CRC16 to the reassembled record.
  It covers every record byte before it (see
  [Reassembly](#reassembly-and-the-record-crc16)).
- **No CRC16**: discovery requests (`0x02`, `0x06`), fragment re-requests,
  and the HMS channel change (`0x56`) carry only the CRC8.

## Discovery

A DTU normally knows its inverters' serials from their labels. The
protocol can also find them over the air. Both discovery requests are sent
to a broadcast address and carry only a CRC8. This is the mechanism the CCC
report describes, so only use it on inverters you own.
[scanner-spec.md](scanner-spec.md) describes how this component uses it.

On nRF24, both are sent to the global Search-ID address `05 64 64 64 64`.
Replies go to the DTU's own address.

### Search ID, opcode `02`

```
02 00 00 00 00 80 00 00 00 00 82
│  └────┬────┘ └────┬────┘ │  └ CRC8 over [0..9]
│       │           │      └ 00
│       │           └ DTU serial (where to reply)
│       └ inverter ID 00000000 = any inverter
└ opcode Search ID
```

Only inverters **not currently bound to a DTU** answer. An HM inverter stops
answering about 15 minutes after a DTU last polled it. Reply (16 bytes, dummy
HM-1200):

```
82 00 00 00 00 80 00 00 00 11 61 00 00 00 00 72
│  └────┬────┘ └────┬────┘ └─┬─┘ └────┬────┘ └ CRC8
│       │           │        │        └ inverter ID repeated
│       │           │        └ product ID (PID), here 1161
│       │           └ DTU serial repeated
│       └ inverter ID = last 8 serial digits
└ 82 = 02 | 80 (reply)
```

The PID narrows down the model family. The report got replies with PIDs
`1021, 1121, 1141, 1144, 1161, 1164, 2801, 2821`.

### Collect RF info, opcode `06`

A fallback that also works while the inverter is bound to a DTU. It has one
more zero byte than Search ID, so the DTU serial is at `[6..9]`:

```
06 00 00 00 00 00 80 00 00 00 00 86
│  └─────┬──────┘ └────┬────┘ │  └ CRC8 over [0..10]
│        │             │      └ 00
│        │             └ DTU serial
│        └ 00 00 00 00 00
└ opcode
```

Reply (11 bytes). Observed inverters reuse opcode `06` instead of `86`. The
reply carries no PID:

```
06 00 00 00 00 00 00 00 00 00 06
│  └────┬────┘ └────┬────┘ │  └ CRC8
│       │           │      └ 00
│       │           └ inverter ID = last 8 serial digits
│       └ 00 00 00 00
└ opcode (06, or 86)
```

A discovery reply never contains the 4-digit model prefix. To configure the
inverter, take the prefix from its label.

## Reading realtime data

### Request: opcode `15`, data type `0B`

The DTU asks for one data type, here `0B` (`RealTimeRunData_Debug`, the live
measurements). 27 bytes, sent at 2026-10-26 12:00:00 UTC to the dummy
HM-1200:

```
15 00 00 00 00 80 00 00 00 80 0B 00 6A DF 40 C0 00 00 00 00 00 00 00 00 54 F3 8C
```

| Bytes | Value | Meaning |
| --- | --- | --- |
| `[0]` | `15` | opcode: multi-frame data request |
| `[1..4]` | `00 00 00 00` | inverter ID |
| `[5..8]` | `80 00 00 00` | DTU serial |
| `[9]` | `80` | multi-frame request |
| `[10]` | `0B` | data type: realtime data |
| `[11]` | `00` | always 0 |
| `[12..15]` | `6A DF 40 C0` | Unix time, big-endian (`0x6ADF40C0` = 1793016000). The inverter sets its clock from it, and "yield today" resets with the date. |
| `[16..17]` | `00 00` | gap, always 0 |
| `[18..19]` | `00 00` | 0 (alarm ID for data type `11`) |
| `[20..23]` | `00 00 00 00` | password, always 0 |
| `[24..25]` | `54 F3` | CRC16 over `[10..23]` |
| `[26]` | `8C` | CRC8 over `[0..25]` |

On nRF24 the inverter's chip ACKs the packet at once. The ACK only means the
radio received it. The inverter's firmware can still reject it, for example if
`[1..4]` do not match its serial.

### Reply fragments: opcode `95`

The answer is longer than one packet, so the inverter splits it into numbered
fragments, one per packet. On HM inverters each fragment has been seen to
carry 16 data bytes, but a receiver should use each packet's length rather
than assume it. The dummy HM-1200 reply has a 62-byte record and a 2-byte
CRC16, so it needs 4 fragments:

```
frag 1  95 00 00 00 00 80 00 00 00 01 00 01 01 59 03 2C 03 1E 0A F1 0A C1 00 12 D6 87 0C
frag 2  95 00 00 00 00 80 00 00 00 02 00 12 4F 80 05 F0 05 D2 01 52 03 16 03 25 0A 6E EC
frag 3  95 00 00 00 00 80 00 00 00 03 0A A1 00 12 02 5A 00 12 2A 64 05 AA 05 C3 09 08 C3
frag 4  95 00 00 00 00 80 00 00 00 84 13 89 29 22 00 0C 01 C7 03 E8 01 9C 00 01 16 CF 64
        │  └────┬────┘ └────┬────┘ │  └──────────────── record bytes ───────────────┘ │
        │       │           │      └ index: 01, 02, 03, then 84 = last, fragment 4    └ CRC8
        │       │           └ DTU serial repeated
        │       └ inverter ID (the sender)
        └ 95 = 15 | 80
```

To accept a fragment, check that:

1. `[0]` is `95`.
2. The CRC8 over `[0..n-2]` equals `[n-1]`.
3. `[1..4]` is the polled inverter, and on HMS, `[5..8]` is our DTU serial.
4. The fragment number `[9] & 7F` is between 1 and 8.

Fragments can arrive out of order, more than once, or not at all. Store
them by number. The fragment that has bit 7 set gives the total count. Until
it arrives, the record is not complete.

### Missing fragments

The DTU can ask again for one fragment `k` with an 11-byte packet whose index
is `80 | k`. For fragment 3:

```
15 00 00 00 00 80 00 00 00 83 16
                           │  └ CRC8
                           └ 80 | 3
```

Ahoy and OpenDTU do this. This component asks for the whole record again
instead, and keeps the fragments it already has.

### Reassembly and the record CRC16

Concatenate the data bytes (`[10..n-2]`) of fragments 1…N in order. The last
two bytes of the result are a CRC16 over all the bytes before them:

```
00 01 01 59 03 2C 03 1E 0A F1 0A C1 00 12 D6 87  00 12 4F 80 05 F0 05 D2 01 52 03 16 03 25 0A 6E
0A A1 00 12 02 5A 00 12 2A 64 05 AA 05 C3 09 08  13 89 29 22 00 0C 01 C7 03 E8 01 9C 00 01 │16 CF│
                                                                                            CRC16
```

`crc16(record[0..61]) = 16CF`. Check it before decoding. Every fragment has
already passed its CRC8, so a mismatch means the record was put together from
the wrong fragments, for example from two different replies. The DTU cannot
tell which fragment is wrong, so it drops them all and asks for the whole
record again. Ahoy and this component (`hm_payload_crc_valid`) both do this.

## The realtime record

All fields are unsigned 16-bit big-endian numbers, except the lifetime
yields (unsigned 32-bit) and the temperature (signed 16-bit). Divide the raw
value by the scale:

| Field | Size | Scale | Unit |
| --- | --- | --- | --- |
| UDC: DC voltage | u16 | 10 | V |
| IDC: DC current | u16 | 100 | A |
| PDC: DC power | u16 | 10 | W |
| YD: yield today | u16 | 1 | Wh |
| YT: yield total | **u32** | 1000 | kWh |
| UAC: AC voltage | u16 | 10 | V |
| F: grid frequency | u16 | 100 | Hz |
| PAC: AC power | u16 | 10 | W |
| Q: reactive power | u16 | 10 | var |
| IAC: AC current | u16 | 100 | A |
| PF: power factor | u16 | 1000 | – |
| T: temperature | **s16** | 10 | °C |
| EVT: event (alarm) counter | u16 | 1 | – |

Bytes `[0..1]` hold a value that none of the references decode (`00 01` in
the example). The inverter's total yield today/total is the sum over its DC
inputs.

## Device control

### Request: opcode `51`

Control commands use opcode `51` with index `81`. `[10]` is the
sub-command, then come its arguments, a CRC16 over `[10..]` and the CRC8:

| `[10]` | Sub-command | Arguments |
| --- | --- | --- |
| `00` | Turn on | `[11]` = `00` |
| `01` | Turn off | `[11]` = `00` |
| `02` | Restart | `[11]` = `00` |
| `0B` | Active power limit | `[11]` = `00`, `[12..13]` limit, `[14..15]` limit type |

Turn off (15 bytes):

```
51 00 00 00 00 80 00 00 00 81 01 00 20 00 71
                           │  │  │  └─┬─┘ └ CRC8
                           │  │  │    └ CRC16 over [10..11]
                           │  │  └ 00
                           │  └ sub-command: turn off
                           └ single frame
```

### Power limit

The limit is a big-endian u16. For relative limits it is the percentage × 10,
for absolute limits watts × 10. The limit type differs between HM and HMS:

| Limit type | HM | HMS |
| --- | --- | --- |
| Absolute, not persistent | `00 00` | `00 00` |
| Relative, not persistent | `00 01` | `00 01` |
| Absolute, persistent | `01 00` | `00 02` |
| Relative, persistent | `01 01` | `00 03` |

"Persistent" means the limit is kept after the inverter restarts. Ahoy sends
the HM values to HMS inverters as well. OpenDTU and this component use the
HMS values. This component only sends relative limits.

50 %, not persistent, to the dummy HM-1200 (19 bytes):

```
51 00 00 00 00 80 00 00 00 81 0B 00 01 F4 00 01 AE 80 81
                           │  │  │  └─┬─┘ └─┬─┘ └─┬─┘ └ CRC8 over [0..17]
                           │  │  │    │     │     └ CRC16 over [10..15]
                           │  │  │    │     └ relative, not persistent
                           │  │  │    └ 500 = 50.0 %
                           │  │  └ 00
                           │  └ active power limit
                           └ single frame
```

70 %, persistent, to the dummy HMS-800:

```
51 00 00 00 00 80 00 00 00 81 0B 00 02 BC 00 03 3D 81 5A
                                    └─┬─┘ └─┬─┘
                          700 = 70.0 %    relative, persistent (HMS)
```

### Confirmation: opcode `D1`

The inverter answers with one packet. Example of an accepted power limit:

```
D1 00 00 00 00 80 00 00 00 81 00 00 0B 00 DB
│                          │  └─┬─┘ │  │  └ CRC8
│                          │    │   │  └ 00 = accepted
│                          │    │   └ sub-command repeated
│                          │    └ 00 00 = accepted
│                          └ 81
└ D1 = 51 | 80
```

Following Ahoy's `parseDevCtrl`, a power limit is accepted when `[10..11]`
are `00 00` and `[13]` is `00`. This component also checks `[13]`. For turn
on, off and restart, any reply counts as a confirmation.

This reply is a single packet that is not repeated. It can be lost even when
the command was carried out. To see the limit the inverter actually uses,
read it back.

## HMS channel change

An HMS inverter that has no DTU (after power-up, or about 15 minutes without
being polled) listens on its region's **boot frequency**. The DTU moves it to
the working frequency with opcode `56`, sent on the boot frequency. The
inverter does not answer. The DTU switches to the working frequency and
polls there.

Move the dummy HMS-800 to EU channel 20 (865 MHz), 15 bytes:

```
56 00 00 00 00 80 00 00 00 02 15 21 14 14 E0
│  └────┬────┘ └────┬────┘ └──┬───┘ │  │  └ CRC8 over [0..13], no CRC16
│       │           │         │     │  └ 14, always
│       │           │         │     └ channel: 0x14 = 20 → 860 + 20 × 0.25 = 865 MHz
│       │           │         └ band: 02 15 21 = 860 MHz band, 03 17 3C = 900 MHz band
│       │           └ DTU serial
│       └ inverter ID
└ opcode channel change
```

This is OpenDTU's layout. Ahoy's `sendSwitchChCmd` also adds a CRC16; this
component follows OpenDTU.

## Exchange timing

### HM (nRF24): channel hopping

1. The DTU sends the request on one of the five channels. The inverter's chip
   ACKs it in hardware. Without an ACK, the DTU resends on the next channel.
   This component tries up to 30 times.
2. The inverter sends its fragments on other channels, starting about 3 steps
   further in the list `3, 23, 40, 61, 75` (wrapping around). For a request on
   channel 23 (index 1), the DTU listens first on index (1 + 3) mod 5 = 4,
   channel 75.
3. For the first 85 ms the DTU switches every 5 ms between "request + 3"
   (channel 75 here) and "request + 2" (channel 61). After that it cycles
   backwards through all five channels.
4. If fragments are still missing, it asks again (for those fragments, or for
   the whole record).

A DevControl confirmation is a single packet, so the DTU just waits on the
"+3" channel.

### HMS (CMT2300A): one frequency

There is no hopping, no ACK and no address filter. The DTU sends the request,
switches to RX on the same frequency and waits up to about 700 ms for the
fragments. One packet takes about 30 ms on air at 20 kbit/s. A lost request
only shows up as silence, so the DTU resends it (this component tries 3
times). If an inverter does not answer at all, the DTU sends the
[channel change](#hms-channel-change) on the boot frequency first and tries
again.

## Other data types

Opcode `15` can ask for other data types in `[10]`. This component only uses
`0B`. The rest are listed here from Ahoy `hmDefines.h` for reference; their
replies are not described in this document.

| `[10]` | Name | Content |
| --- | --- | --- |
| `00` | InverterDevInform_Simple | firmware version, simple |
| `01` | InverterDevInform_All | firmware and hardware versions |
| `02` | GridOnProFilePara | grid profile |
| `05` | SystemConfigPara | current power limit, among others |
| `0B` | RealTimeRunData_Debug | live measurements (this document) |
| `0C` | RealTimeRunData_Reality | |
| `0D`/`0E`/`0F` | RealTimeRunData_A/B/C_Phase | three-phase models |
| `11` | AlarmData | event log; `[18..19]` = last alarm ID received |
| `15` | GetLossRate | radio statistics |
