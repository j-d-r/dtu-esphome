# HM/nRF24 + HMS/CMT2300A Reference Notes

Project scope:

- HM-series inverters over nRF24L01+ (verified on hardware).
- HMS-series inverters over CMT2300A (implemented, **not yet hardware-verified**).
- HMT (3-phase, 6-channel) is intentionally out of scope: it needs a
  three-phase AC telemetry struct and 6 DC channels, neither of which this
  component models.

Sources consulted:

- Ahoy `src/hm/NrfRadio.h`, `Radio.h`, `Communication.h`, `hmDefines.h`,
  `hmInverter.h`, `hmSystem.h`, `src/hms/{cmt2300a,CmtRadio,esp32_3wSpi,cmtHal,hmsDefines}.h`,
  and `utils/crc.*` from `https://github.com/lumapu/ahoy`.
- OpenDTU `lib/Hoymiles/src/{HoymilesRadio_CMT.cpp,Hoymiles.cpp}`,
  `src/inverters/HMS_{1CH,1CHv2,2CH,4CH,Abstract}.cpp`,
  `src/commands/{ChannelChangeCommand,ActivePowerControlCommand,CommandAbstract}.cpp`,
  and `lib/CMT2300a/{cmt2300a.c,cmt2300a_defs.h,cmt2300wrapper.cpp,cmt2300a_params_{860,900}.h}`
  from `https://github.com/tbnobody/OpenDTU`.
- ESPHome 2026.6.2 local package and generated build headers for SPI device,
  GPIO interrupt, loop wake, sensor, and text sensor codegen patterns.

Implementation policy:

- Ahoy and OpenDTU are used as communication references only.
- This component keeps a clean ESPHome-native implementation in this repo.
- Do not copy Ahoy source into this component unless licensing is revisited
  (Ahoy is CC-BY-NC-SA, which is incompatible with this repo's GPL-3.0-only).
  OpenDTU is GPL-2.0-or-later, so its code may be used, with attribution in
  NOTICE (which also lists the OpenDTU-derived data); nothing is vendored today. The CMT2300A
  register banks are hardware configuration data generated by CMOSTEK's own
  RFPDK tool and published identically by the vendor, OpenDTU and Ahoy.

Protocol facts used by the first HM 4-channel milestone:

- nRF24: 1 MHz SPI mode 0, 250 kbps RF rate, CRC16, dynamic payloads,
  5-byte addresses, channel list `3, 23, 40, 61, 75`.
- Inverter nRF address is four low serial bytes reversed into bytes 4..1,
  with byte 0 set to `0x01`.
- Read-only polling uses request `0x15` / payload command `0x0B`.
- HM 4-channel realtime payload is expected in seven fragments.
- Frame CRC is CRC8 polynomial `0x01`, init `0x00`.
- Payload control CRC is CRC16/Modbus polynomial `0xA001`, init `0xFFFF`.
- RX pipe/address setup: Ahoy `NrfRadio.h::setup()` opens the reading pipe on
  the DTU's own radio id; `sendPacket()` opens the writing pipe on the target
  inverter's radio id (RF24 pipe 0 handles the TX ACK).
- On TX ACK, Ahoy sets HM `rxOffset = 3`, starts RX on `(txCh+3) % 5`. For the
  first `DURATION_TXFRAME = 85ms` it pendulates RX between `txCh+3` and
  `txCh+2` (channel dwell `DURATION_LISTEN_MIN = 5ms`), then falls back to a
  reverse sweep through all five channels. These map to this component's
  `RX_INITIAL_PENDULUM_MS` / `RX_CHANNEL_DWELL_MS` constants.
- Ahoy's retransmit setup is `setRetries(3, 15)`.

## HMS / CMT2300A facts, 2026-09-30

Cross-checked between Ahoy and OpenDTU; where they disagree it is called out.

- The **application protocol is identical** to HM: same `initPacket` framing
  (`[0]` opcode, `[1..4]` inverter radio id, `[5..8]` DTU id, `[9]` frame id),
  same CRC8-over-all / CRC16-over-control-data rules, same realtime request
  (`0x15` + sub-command `0x0B` + epoch), same fragment assembly with the `0x80`
  last-fragment bit, same `0x01`+reversed-serial radio id derivation. Only the
  radio and the record offsets differ, which is why `protocol.{h,cpp}` is shared.
- **Radio**: GFSK, 20 kbps, 20 kHz deviation, 4-byte sync word, variable-length
  packets, IBM-16 CRC, FEC enabled, preamble 30 bytes TX / 2 RX. Configuration
  comes from RFPDK-generated register banks (see below).
- **Frequency**: channel index counts 250 kHz steps up from the band base
  (`FREQ_OFS = 100`, i.e. 100 x 2.5 kHz). EU base 860 MHz, legal 863-870, DTU
  work frequency 865 MHz (channel 20), inverter boot frequency 868 MHz
  (channel 32). US base 900 MHz, legal 905-925, work 918, boot 915. Brazil base
  900 MHz, legal 915-928, work 918, boot 915. Source: OpenDTU
  `countryDefinition`; Ahoy's `getBaseFreqMhz`/`getBootFreqMhz` agree.
- **No addressing, no ACK**: the CMT2300A has neither an address filter nor
  auto-ACK, so received packets must be matched in software on the DTU id at
  `[5..8]` (OpenDTU does the same in `HoymilesRadio_CMT::loop`), and there is no
  TX_DS-equivalent - a lost request is only visible as silence.
- **Frequency binding**: an inverter that lost its DTU falls back to the boot
  frequency after ~15 min. The channel-change command (`0x56`) moves it:
  `[9..11]` = `02 15 21` on the 860 MHz band / `03 17 3C` on the 900 MHz band,
  `[12]` = target channel, `[13]` = `0x14`, then **CRC8 only** (15 bytes total,
  no CRC16). It is never answered. OpenDTU sends it before polling an
  unreachable inverter, on the boot frequency; this component does the same.
  Ahoy's `sendSwitchChCmd` appends a CRC16 as well - OpenDTU's capture-derived
  layout (CRC8 only) is the one used here.
- **Record layouts** (`hm_model_layout`): Ahoy `hms{1,2,4}chAssignment` and
  OpenDTU `HMS_{1CH,2CH,4CH}` agree byte for byte. HMS 1-channel is identical to
  HM 1-channel. HMS 2-channel (len 42) and HMS 4-channel (len 66) interleave the
  DC channels differently from their HM counterparts, and HMS 4-channel reports
  a voltage per input rather than one per MPPT pair.
- **HMS-450/500 v2** (serial prefix 1125/1400) is the one unresolved
  disagreement: OpenDTU `HMS_1CHv2` decodes one DC channel from the 2-channel
  offsets but takes the event code from 18 and reactive power from 20 (len 40),
  where Ahoy uses the plain 2-channel assignment (event code 40, reactive power
  32, len 42). This component follows OpenDTU and flags both fields as
  unverified.
- **Power limit**: the DevControl request is identical except for the control
  word. HM: `RelativNonPersistent` `0x0001`, `RelativPersistent` `0x0101`. HMS:
  `0x0001` / `0x0003` (OpenDTU `_powerLimitControlTypeValues`). Ahoy sends the HM
  words to HMS inverters too; OpenDTU treats that as a bug, and this component
  follows OpenDTU.
- **Serial prefixes** (OpenDTU `HMS_*::isValidSerial`, cross-checked with Ahoy
  `hmSystem.h`): 1124 -> HMS-300/350/400/450/500 (1ch); 1125, 1400 -> HMS-450/500
  v2; 1143, 1144, 114A, 1410 -> HMS-600/700/800/900/1000 (2ch); 1164, 1166, 1420
  -> HMS-1600/1800/2000 (4ch).
- **Register banks**: the 0x00-0x5F register file is loaded from RFPDK output.
  Only the frequency bank (0x18-0x1F) and register 0x27 (`0x0A` on 860 MHz,
  `0x0B` on 900 MHz) differ per band. OpenDTU's
  `cmt2300a_params_{860,900}.h` and Ahoy's `cmtConfig` contain the same values.
- **Init sequence** (CMOSTEK `CMT2300A_Init` + OpenDTU `_init_radio`): soft reset
  (`0x7F` = `0xFF`), 20 ms, go STBY, presence self-test (write/read `0xAA` at
  PKT17 `0x48`), set `CFG_RETAIN` and clear `RSTN_IN_EN` in MODE_STA, set
  `LOCKING_EN` in EN_CTL, disable LFOSC, clear interrupt flags, load the banks,
  `xosc_aac_code = 2` in CMT10, GPIO2 -> INT1 / GPIO3 -> INT2, INT1 = TX_DONE and
  INT2 = PKT_OK, enable TX_DONE/PREAM_OK/SYNC_OK/CRC_OK/PKT_DONE, `FREQ_OFS` =
  100, enable FIFO merge, set the TX power word, then a sleep/standby cycle for
  the configuration to take effect.
- **TX**: STBY, clear flags, select FIFO write, clear TX FIFO, write the length
  to PKT15 (`0x46`), write the FIFO, check `TX_FIFO_NMTY`, go TX, then poll
  `INT_CLR1` for `TX_DONE_FLG` (this component polls it from `loop()` instead of
  busy-waiting as both references do; a packet is ~30 ms on air).
- **RX**: STBY, clear flags, select FIFO read, clear RX FIFO, go RX. A packet is
  ready when `INT_FLAG` has PREAM_OK|SYNC_OK|CRC_OK|PKT_OK all set (Ahoy's gate;
  OpenDTU gates on PKT_OK alone). The FIFO is length-prefixed: the first byte
  read is the payload length. RSSI is `reg 0x70 - 128` dBm.
- **TX power**: the dBm -> TX8/TX9 word table is OpenDTU's `setPALevel` (valid
  for the 20 dBm matching network the parameter set assumes); above +16 dBm the
  CMT4 bit0 "double" flag is also needed.
- **3-wire SPI**: 16-bit register frame (bit15 R/W, bits 14-8 address, bits 7-0
  data) on CSB; 8-bit FIFO transfers on FCSB with >2 us between bytes; SDIO is
  released to input for the data phase of a read. Both references drive this with
  the ESP32 hardware SPI peripheral in half-duplex 3-wire mode (Ahoy's variant
  additionally inverts the signal in the GPIO matrix and pre-inverts the data in
  software, which cancels out). This component does the same on ESP32. It has
  two devices on one bus, one with CSB and one with FCSB as hardware chip select,
  using OpenDTU's CS timing at 1 MHz. The host is one that no ESPHome `spi:` bus
  took (`_cmt_spi_host_index` in `hoymiles_dtu_cmt/__init__.py`). Bit-banging on plain GPIOs is
  kept as the fallback when no host is free. The transport is the main thing the
  HIL checklist in `tests/manual/hms_cmt/` has to prove.

## ESPHome API notes

- `automation.register_action(...)` requires an explicit `synchronous=`
  keyword; action classes that complete all work inside `play()` (including
  ones that just queue state for a state machine to pick up later) should
  register with `synchronous=True`.
- Trivially-copyable `TEMPLATABLE_VALUE(...)` fields need Python codegen to
  pass values through `cg.templatable(value, args, type)` before calling
  setters.
- `Component::enable_loop_soon_any_context()` (declared in
  `esphome/core/component.h`) is `IRAM_ATTR`-safe; it sets the component's
  pending loop-enable flag and calls `wake_loop_any_context()`.
- `HighFrequencyLoopRequester` (declared in `esphome/core/helpers.h`) —
  `start()`/`stop()` from normal loop context only while a radio exchange is
  active.
- `GPIOPin` has no interrupt API; interrupt attachment requires
  `InternalGPIOPin::attach_interrupt(func, arg, gpio::INTERRUPT_FALLING_EDGE)`.
- ISR handlers must not perform SPI, logging, parsing, publishing, or
  `HighFrequencyLoopRequester` state changes. The nRF IRQ handler should only
  set an ISR-safe flag and call `enable_loop_soon_any_context()`.
- `cv.polling_component_schema(default)` extends `COMPONENT_SCHEMA` and adds
  `update_interval:`; `cg.register_component()` calls `set_update_interval()`
  automatically when `CONF_UPDATE_INTERVAL` is present in config, so
  `PollingComponent` subclasses don't need to wire it by hand.
- SPI host ownership (checked 2026-10-25 against installed 2026.10.0 and the
  2026.6.3 tag CI uses). On ESP32, `spi:` uses the ESP-IDF SPI master driver
  under both Arduino and ESP-IDF (`get_spi_interface()` returns
  `SPI2_HOST`/`SPI3_HOST`). It assigns hosts while the `spi` config is
  validated and stores each one as `interface_index` on the bus, so a
  component's final validation can see which hosts are free.
  `get_hw_interface_list()` lists `spi2` + `spi3`, or only `spi2` on
  C2/C3/C5/C6/C61/H2/H21. Its devices never set `SPI_DEVICE_3WIRE`. A bus with
  no MISO only gets `SPI_DEVICE_HALFDUPLEX`, so the CMT2300A cannot be an
  ordinary `spi:` device.
- ESPHome now excludes unused built-in IDF components from the build
  (`DEFAULT_EXCLUDED_IDF_COMPONENTS` in `components/esp32/__init__.py`;
  re-enable with `include_builtin_idf_component()`). `esp_driver_spi` is not
  excluded, but the legacy `driver` shim is. So include
  `driver/spi_master.h`, which lives in `esp_driver_spi`, and nothing else
  from `driver/`.

## HM model families and realtime payload layout, 2026-07-01

Verified against Ahoy `src/hm/hmDefines.h` (`hm1chAssignment`, `hm2chAssignment`,
`hm4chAssignment`). Ahoy groups HM inverters by DC-input count; the realtime
record layout depends only on that count, so this component keys the parser on it:

- 1 channel: HM-300 / HM-350 / HM-400 (`HM1CH_PAYLOAD_LEN` 30).
- 2 channels: HM-600 / HM-700 / HM-800 (`HM2CH_PAYLOAD_LEN` 42).
- 4 channels: HM-1000 / HM-1200 / HM-1500 (`HM4CH_PAYLOAD_LEN` 62).

Field byte offsets in the assembled record (`u16` big-endian unless noted; the
common divisors are UDC/10, IDC/100, PDC/10, YD/1, YT(`u32`)/1000, UAC/10,
IAC/100, PAC/10, Q/10, F/100, PF/1000, T(`int16`)/10, EVT/1):

| Field | 1ch | 2ch | 4ch |
| --- | --- | --- | --- |
| CH1 UDC/IDC/PDC | 2 / 4 / 6 | 2 / 4 / 6 | 2 / 4 / 8 |
| CH1 YD / YT | 12 / 8 | 22 / 14 | 20 / 12 |
| CH2 UDC/IDC/PDC | - | 8 / 10 / 12 | =CH1 / 6 / 10 |
| CH2 YD / YT | - | 24 / 18 | 22 / 16 |
| CH3 UDC/IDC/PDC | - | - | 24 / 26 / 30 |
| CH3 YD / YT | - | - | 42 / 34 |
| CH4 UDC/IDC/PDC | - | - | =CH3 / 28 / 32 |
| CH4 YD / YT | - | - | 44 / 38 |
| UAC / F / PAC | 14 / 16 / 18 | 26 / 28 / 30 | 46 / 48 / 50 |
| Q / IAC / PF | 20 / 22 / 24 | 32 / 34 / 36 | 52 / 54 / 56 |
| T / EVT | 26 / 28 | 38 / 40 | 58 / 60 |

`=CHn` means the input shares the paired channel's voltage (Ahoy `CALC_UDC_CH`).
These offsets live in `hm_model_layout()` in `protocol.cpp` and are unit-tested in
`tests/native/test_protocol.cpp`.

## Extra serial prefixes, 2026-10-25

Source: OpenDTU `lib/Hoymiles/src/inverters/{HM_*,HMS_*}.cpp` `isValidSerial()`,
from a local OpenDTU checkout (fork `j-d-r/OpenDTU-private`, commit `8da432d5`);
the older OpenDTU copy has the same serial rules.

Prefixes accepted by the build-time model/serial check:

- HMS 2-channel 1146 and HMS 4-channel 1421: OpenDTU only.
- HM 1022 / 1042 / 1062 (1/2/4 channels): MI 3rd-generation inverters, which
  OpenDTU (`HM_*::isValidSerial`) and Ahoy (`hmSystem.h`, serial byte 5 == 0x10
  with `b4 & 0x03 == 0x02`) both treat as HM.
- OpenDTU's HM rule is wider still (any `x12x` / `x14x` / `x16x` prefix not
  claimed by an HMS family first); this component keeps an explicit list,
  since the check only warns.

## HERF models, 2026-10-25

Source: OpenDTU `lib/Hoymiles/src/inverters/{HERF_1CH,HERF_2CH,HERF_4CH}.cpp`
`isValidSerial()` and `byteAssignment[]`, from the same OpenDTU checkout as above.
Ahoy has no HERF support. Not hardware-verified.

- **HERF** inverters are nRF24 (OpenDTU derives them from `HM_Abstract` /
  `HM_4CH` and attaches them to the nRF24 radio). Prefixes: 2841 -> HERF-300,
  2821 -> HERF-600/800, 2801 -> HERF-1600/1800.
- **Record layouts:**
  - HERF-600/800 are byte for byte the HMS 2-channel layout.
  - HERF-1600/1800 are the HM 4-channel layout (`HERF_4CH` subclasses `HM_4CH`).
  - HERF-300 has its own layout: DC fields at the HMS-450/500 v2 offsets
    (UDC 2, IDC 6, PDC 10, YT 14, YD 22), AC fields at the 2-channel offsets
    (UAC 26, F 28, PAC 30, IAC 34, PF 36), T 38, length 42. OpenDTU reads both
    reactive power and the event code from offset 40, and marks Q, T and EVT
    "to be verified"; this component does the same.
